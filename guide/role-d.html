PART 1 · 요구사항 정의서 작성 (핵심)

"무엇을 만들 것인가"를 문서로 못박는 작업이에요. 아래 4가지 묶음으로 구성하면 깔끔합니다.

① 기능 요구사항 (FR)

시스템이 해야 하는 일. "~할 수 있어야 한다" 형태로. 각 항목에 ID·우선순위.

ID요구사항우선순위
FR-1사용자는 증상을 자연어(텍스트)로 입력할 수 있어야 한다필수
FR-2정보가 부족하면 시스템은 추가 질문을 되물을 수 있어야 한다필수
FR-3시스템은 증상에 맞는 진료과를 근거와 함께 추천(Top-3)해야 한다필수
FR-4시스템은 주변 병원·약국·응급실을 안내해야 한다필수
FR-5응급 증상이면 분류를 건너뛰고 119·응급실을 즉시 안내해야 한다필수
FR-6(확장) 사용자는 음성으로 증상을 입력할 수 있다선택

② 비기능 요구사항 (NFR)

시스템의 품질·제약. 성능·안전·보안 등.

ID요구사항
NFR-1 (안전)모든 응답에 "의학적 진단이 아닌 참고용 안내"임을 표시한다
NFR-2 (안전)응급 판별은 미탐(놓침)을 최소화하도록 보수적으로 동작한다
NFR-3 (가용성)외부 API 장애 시에도 서비스가 중단되지 않는다(예외 처리·폴백)
NFR-4 (성능)일반 질의 응답은 수 초 이내에 반환한다
NFR-5 (보안)API 키는 코드에 하드코딩하지 않고 .env로 관리한다

③ 사용자 시나리오 (유스케이스)

대표 흐름을 글로. 예:

[일반 시나리오]
1. 사용자가 "오른쪽 아랫배가 아프고 열이 나요" 입력
2. 시스템이 통증 양상·동반 증상을 되물음
3. 사용자가 추가 답변
4. 시스템이 '외과(87%)' 등 Top-3 진료과를 근거와 함께 제시
5. 주변 외과 병원 목록을 지도/리스트로 안내

[응급 시나리오]
1. 사용자가 "갑자기 가슴이 쥐어짜듯 아파요" 입력
2. 시스템이 응급으로 판단 → 즉시 119·응급실 안내

④ 제약사항

  • 공공데이터포털 개발계정 트래픽 제한(일일 한도)
  • LLM은 수업 제공 GPT(OpenAI) 키 사용
  • 로컬/시연 환경에서 동작 (상시 운영 아님)

PART 2 · 기획서 관리

  • 교수님 양식(틀)은 유지하고, 내용만 최신으로 반영 (기술스택·흐름도가 바뀌면 동기화)
  • 개발이 진행되며 바뀐 결정(예: 프론트+FastAPI, GPT 확정 등)을 기획서에 반영
  • 최신본 1개만 유지, 이전 버전은 날짜로 구분하거나 정리

PART 3 · 보고서

중간/최종 보고서 뼈대:

# 최종 보고서
1. 프로젝트 개요 (주제·목표)
2. 시스템 구성 (흐름·기술스택)      ← 설계문서(박근령)에서 가져옴
3. 구현 내용 (기능별)
4. 평가 결과 (Top-3 정확도 등)       ← 박태준에게서
5. 한계 및 향후 계획
6. 역할 분담 / 소감

2·4번처럼 다른 담당의 산출물을 받아서 엮는 게 D의 역할이에요.

최종 체크리스트

  • □ 요구사항 정의서 (FR · NFR · 유스케이스 · 제약) 작성
  • □ 기획서 최신 내용 반영 (바뀐 결정 동기화)
  • □ 중간/최종 보고서 작성 — 평가 결과 반영
  • □ 표준 용어집대로 문서 전체 통일
  • □ 제출 문서 형식·마감 확인
팁 — 요구사항 정의서는 개발 초반에 한 번 잘 써두면, 각자 "내가 뭘 만들어야 하는지"의 기준이 돼요. FR 목록이 곧 구현 체크리스트가 됩니다.
